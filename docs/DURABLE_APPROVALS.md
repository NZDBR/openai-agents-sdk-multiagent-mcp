# Durable approval execution

Approvals commit to Lakebase together with an outbox entry. The HTTP handler never submits a Job or invokes OpsTask. A scheduled Databricks dispatcher submits execution Jobs using a stable idempotency token per approval/retry generation. A separate execution Job loads the reviewed payload, validates it, claims an expiring lease, and invokes the backend-only writer with the approval ID as the business idempotency key. No worker service or immediate-dispatch path is introduced.

Approval states: PENDING_APPROVAL → APPROVED / REJECTED / EXPIRED. Execution states: NOT_STARTED → QUEUED → EXECUTING → EXECUTED / RETRYABLE_FAILURE / FAILED. Approval and execution are independent; an approved proposal expiring before its next write attempt becomes FAILED/EXPIRED without rewriting its approval decision. Rejected or expired pending proposals never enter execution. A side effect already performed before expiry is not undone; late confirmed results may be recorded while the worker still owns its lease. Unconfirmed expired side effects require reconciliation.

## Selected-resource migration and deployment

1. Back up the deliberately selected Lakebase database/schema. Stop App writes and pause the dispatcher/executor during migration. Never provision a random catalog or schema.
2. For a fresh database apply `resources/schema.sql`. For the existing pre-durability table apply **only** `resources/migrations/002_durable_approvals.sql` once. `CREATE TABLE IF NOT EXISTS` does not migrate an old table. Replace `store_ops` consistently if using a different schema. Before the migration, execute `SELECT set_config('store_ops.migration_tool_name', '<actual-create-tool-name>', false)` in the same database connection, with your selected schema prefix instead of `store_ops` where appropriate. The migration requires this explicit tool binding and aborts without it.
3. Legacy pending proposals become expired and need fresh proposals/review. Existing completed/rejected records are preserved. Legacy executing/needs_reconciliation rows become FAILED with LEGACY_RECONCILIATION_REQUIRED and are **not enqueued**. Keep approvals_legacy read-only until reconciliation/retention review. Do not reset failed records or replace idempotency keys to bypass uncertain outcomes.
4. Supply root DAB variables `approval_service_principal`, `approval_secret_scope`, `approval_client_id_key`, `approval_client_secret_key`, existing cluster/Lakebase/MCP values, and `approval_policy`. All identifiers remain generic. The worker retrieves M2M secrets using `dbutils.secrets`; secret values are never notebook parameters. Demo mode instead retrieves its isolated synthetic write token from the configured demo secret scope.
5. Grant the dispatcher principal Lakebase access and CAN_MANAGE_RUN on the execution Job (the DAB includes the Job grant). Grant the worker principal Lakebase access and READ only on its secret scope. Grant the M2M writer principal only the selected OpsTask-write invocation permission and upstream store/assignee permissions. The Job's native identity accesses Lakebase; the dedicated M2M identity accesses the write MCP. The two may be deliberately configured as the same principal. Remove any previous App SP writer grant or secret ACL; deleting a bundle binding is not proof that inherited/manual grants were revoked.
6. Runtime SQL roles need SELECT/INSERT/UPDATE on approvals and outbox; approval_events needs INSERT and its sequence USAGE for the invoker trigger. Restrict audit SELECT to operators. Deny runtime audit UPDATE/DELETE, table/function ownership, DDL and trigger-disable privileges. Migration uses a separate privileged identity. These constraints do not defend against a database administrator.
7. Build wheels, stage Apps, validate dev/prod/demo configuration, and deploy the selected DAB target. Verify native Jobs identity, Lakebase commits, secret ACLs, MCP denial, idempotency contract and lease recovery in that workspace. Only then explicitly override `resources.jobs.store_operations_approval_dispatch.schedule.pause_status: UNPAUSED`. It defaults to PAUSED. The one-minute schedule is administrator-editable through the root DAB.

## Limits, retries and fencing

`approval_policy` is JSON with ttl=86400, lease=120, timeout=45, retries=5, backoff=30, backoff_cap=3600. Time values are seconds; retries bounds total failed execution attempts including abandoned leases. The same JSON is bound to App and both Jobs as APPROVAL_POLICY_JSON. Local environment overrides APPROVAL_TTL, APPROVAL_LEASE, APPROVAL_TIMEOUT, APPROVAL_RETRIES, APPROVAL_BACKOFF and APPROVAL_BACKOFF_CAP are supported. All must be positive; the lease must exceed twice the MCP timeout. Notebook task timeout is 300 seconds and native task retries are disabled; durable state owns retries.

The dispatcher recovers expired execution leases, inserts due retry generations, and checks submitted Jobs that terminated before persisting a result. Submission retries reuse the same Jobs token, including after an accepted submission loses its response. Worker retry generations use a different submission token but the **same OpsTask business key**. Dispatch leases prevent normal duplicate submissions; conditional lease-token updates fence stale dispatchers and execution workers. Failed submissions have their own bounded count and persisted backoff in the outbox.

Transport timeouts/disconnections, MCP connection-closed errors, HTTP 408/429 and selected 5xx responses are retryable. Generic MCP tool errors, schema/action mismatches, forbidden responses, and unconfirmed/unsupported Gateway ASK outcomes fail closed. Only fixed error codes are persisted; raw error text, credentials, URLs and payloads are excluded. A failed/ambiguous action needs operator reconciliation by approval ID before a replacement proposal. No automatic ASK acceptance is implemented.

The worker revalidates approval, expiry, action/tool/store binding, exact reviewed payload and idempotency key. It rechecks its lease/expiry immediately before the MCP mutation. A stale worker cannot persist a result after lease expiry or replacement. It cannot cancel an external request already in flight: **the external provider must durably enforce same-key/same-payload replay and reject same-key/different-payload reuse**. Without that production provider contract, exactly-once external task creation cannot be claimed. The demo provider implements and tests this contract. The design provides bounded retry/recovery, not an unconditional eventual-success guarantee during indefinite outages.

The database freezes reviewed content, ownership, expiry and action binding from insertion (stronger than post-approval only), and freezes the human decision after it leaves pending. Approval events record proposal/decision/attempt/retry/result transitions with timestamps. `retry_count` counts failures, not successful calls; `last_attempt_at` and audit events preserve attempt history. Retention and operator reconciliation remain administrative tasks.

## UI and validation scope

The approval card displays task title, store, assignee, due date, action, created/expiry times, approval status/ID and controls. View details contains exact reviewed JSON. Execution status is separate; status refresh polls every ten seconds. Public SQL projections omit employee/session IDs, tool binding, idempotency key, retry details, errors and leases.

`tests/test_durable_approvals.py` uses actual local PostgreSQL, real schema/migration/constraints and concurrent connections. Set TEST_POSTGRES_DSN to a disposable local database; tests create/drop unique schemas. CI provides PostgreSQL 16. Without that variable the database tests skip explicitly. Jobs calls are fake, external side effects use the synthetic OpsTask repository, and OAuth uses test credentials. Run `uv run pytest -q`, the three-process MCP validator, frontend build, both wheels, staging, and dev/prod/demo configuration validators.

No local result proves live Lakebase OAuth/commit durability, Job scheduling/token deduplication/run identity, production OpsTask idempotency or permissions. Those require deliberately configured live resources. The existing opt-in live session test is not a durability acceptance test for approvals.
